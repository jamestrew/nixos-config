# Change log — intent behind each personalization

Recorded so local intent can be re-expressed when upstream changes overlap a personalization. The updater uses the pinned upstream commit as the merge baseline and this file for the human judgment a three-way merge cannot supply.

## Theme

The upstream skills are deliberately tracker-agnostic: they defer to a per-repo config file (`docs/agents/issue-tracker.md`) generated by `/setup-matt-pocock-skills`, and carry parallel code paths for local markdown, GitHub, GitLab, and "other". This machine uses **GitHub exclusively**, so that indirection buys nothing and costs a setup step plus a config file that must exist before the skills work at all.

Three decisions drive every change below:

1. **Bake GitHub in.** Delete the abstraction layer and the `/setup-matt-pocock-skills` dependency.
2. **Use GitHub's native issue dependencies** for blocking, rather than prose in the issue body.
3. **Don't teach the model `gh`.** Saying "via the `gh` CLI" is enough; the models in use already know how to create and label issues. Only genuinely non-obvious API details are spelled out — see [What's kept and why](#whats-kept-and-why).

## What's kept and why

Everything explicit in these skills earns its place by being something a model plausibly gets wrong:

| Kept detail | Why it isn't obvious |
| --- | --- |
| `--blocked-by` / `--blocking` / `--parent` on `gh issue create` | Recent flags; a model may not know they exist and would otherwise write prose edges or reach for the raw dependencies API. |
| `gh issue edit --add-blocked-by` / `--remove-blocked-by` | Same. Corrects an edge without recreating the issue. |
| Publish blockers-first | Load-bearing constraint, not style: `--blocked-by` takes issue numbers, so a blocker must exist first. |
| Create the label before using it | `gh` fails the *whole* create/edit on an unknown label. Upstream got its label vocabulary from the setup skill; without it this is a real failure mode. |
| `issueDependenciesSummary.blockedBy` vs `blockedBy.totalCount` | A genuine footgun — see the wayfinder entry. |
| `authorAssociation` values for "external" PR | The specific enum members are worth naming. |

A fourth decision covers review, and is independent of the three above:

4. **Review is done by `thermonuclear-review`**, a locally-authored skill outside this repo. Upstream's `code-review` is removed rather than personalized.

## `triage/SKILL.md`

1. **Issues are GitHub issues, worked via `gh`** — opening line.
2. **PRs as a triage surface** — upstream read this off a config flag defaulted **off**. Now: issues by default, PRs when the maintainer asks. Same effective behaviour, no config. Added the GitHub-specific note that issues and PRs share one number space, so a bare `#42` may be either.
3. **Label vocabulary** — upstream said the canonical role names may map to different label strings and to run the setup skill for the mapping. Now the role names *are* the label strings, with an instruction to create missing ones rather than substitute a near-match (unknown label = failed edit).
4. **"External" PR filter** — upstream deferred to "the tracker config defines who counts as external". Now names the `authorAssociation` values directly: keep `CONTRIBUTOR` / `FIRST_TIME_CONTRIBUTOR` / `NONE`, drop `OWNER` / `MEMBER` / `COLLABORATOR`.

## `wayfinder/SKILL.md`

1. **Frontmatter description and intro** — "on your issue tracker" → GitHub.
2. **Removed the tracker-doc deferral.** Upstream pointed at the tracker doc's "Wayfinding operations" section for map/ticket/blocking/frontier mechanics, defaulting to local markdown if absent. Replaced with one sentence naming the native relationships: `--parent` to hang a ticket off the map, `--blocked-by` for blocking, assignment to claim.
3. **Tickets are sub-issues** (`--parent`), identified by issue number — upstream said "child issue" and "the tracker's issue id".
4. **The frontier-count footgun** — the one substantive addition. `blockedBy.totalCount` (from `gh issue list --json blockedBy`) counts **all** blockers including closed ones; the live gate is the GraphQL field `issueDependenciesSummary.blockedBy`, which counts only open ones. Gating on the wrong one means a ticket whose blockers have all been resolved still looks blocked and **the frontier never advances** — a silent deadlock. This lives in wayfinder rather than `to-tickets` because wayfinder is where frontier queries actually happen; `to-tickets` only creates edges.

- Skill directory deleted from the local collection.

**What was lost with it:** upstream `code-review` ran **two axes** — Standards *and* **Spec** ("does the diff faithfully implement the originating issue/PRD?"). `thermonuclear-review` covers maintainability only; it has no spec-conformance axis. See the note in the `implement` entry below.

## `implement/SKILL.md`

Upstream was six lines ending in "Once done, use /code-review to review the work." Rewritten around a phased review loop.

Kept deliberately terse — anything an agent would do anyway was cut. Four things earn their place:

1. **Never read or invoke `thermonuclear-review` in the main agent**, with a one-line reason. The reason stays because this is the kind of instruction an agent otherwise "helpfully" violates; without it, the implementer reviews its own work against a rubric it just read.

2. **Termination via an explicit `VERDICT:` line**, judged against the review skill's own approval bar.
   *Why:* "loop until it raises no issues" needs a checkable stop condition. `thermonuclear-review` is deliberately extremely strict, so a literally zero-finding round would be rare and terminating on "no findings" risks spinning forever. Delegating the verdict to its own approval bar makes stopping *its* judgment.

3. **Declined findings carry forward** into the next round's prompt. Fresh eyes each round is the point, but a reviewer with no memory re-raises settled points forever. The review skill already treats findings as presumptive blockers that a clear justification can answer, so declining is legitimate — dropping one silently is not.

4. **Hard cap of three rounds**, then hand to the user. Three unconverged rounds indicates a disagreement or design problem another round won't settle.

"Report findings only — do not edit" lives inside the subagent prompt rather than as its own rule, so the branch keeps one writer.

**Open gap — spec conformance.** Removing `code-review` removed the only spec-conformance check; `implement` still says "implement the work described in the spec or tickets", but nothing verifies the result against it. If that matters, the cheapest fix is a line in `implement`'s final checks to verify acceptance criteria against the ticket before review. Deliberately not added — it wasn't asked for, and the main agent already holds the spec in context.

## `teach` HTML color pallete

Added
```md
Unless the learner has given different visual preferences, start HTML lessons and references with this dark, warm-charcoal palette. It is intentionally softer than a near-black theme, keeps code blocks visually distinct, and declares `color-scheme` so native controls match. Treat these as reusable design tokens in the shared stylesheet rather than scattering literal colors through lesson files:

```css
:root {
  color-scheme: dark;
  --paper: #20242b;
  --ink: #e8e6df;
  --muted: #aaa69d;
  --line: #464c57;
  --accent: #f09a7c;
  --accent-soft: #342925;
  --code: #181b20;
  --success: #79c99e;
  --error: #ff8e8e;
}
```

Reference documents should still print cleanly. In `@media print`, switch `color-scheme` to `light` and redefine the same tokens to a white-paper palette. A learner's stated theme or accessibility preference always takes precedence over this default.
```
